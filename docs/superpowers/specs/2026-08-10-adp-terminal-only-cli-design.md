# ADP terminal-only CLI design

## Цель

Добавить режим `--terminal-only`, который выполняет single- или multi-index
эксперимент без каких-либо записей в файловую систему и печатает читаемую
агрегированную сводку в терминал.

## Интерфейс

`ADP/cli.py` принимает новый флаг `--terminal-only`. Он работает с ручной
конфигурацией и с `--experiment-file`; `--no-progress` продолжает управлять
progress bars.

`--terminal-only` несовместим с `--resume` и `--reports-only`, потому что эти
режимы требуют существующего файлового архива. `--dry-run` остаётся отдельной
проверкой конфигурации и числа jobs без fit.

## Выполнение без персистентности

Runner валидирует experiment и строит jobs тем же способом, что и обычный
режим. Данные для каждой пары `(point, seed)` создаются один раз, хранятся
только в памяти и последовательно передаются всем вариантам. Это сохраняет
paired-сравнимость и чередование порядка вариантов.

В terminal-only режиме runner не создаёт `_SeriesStore`, output-каталог или
временные файлы и не вызывает функции сохранения NPZ, commits, CSV, моделей и
отчётов. Результат каждого job хранится в памяти до построения сводки. Ошибка
одного job получает статус `numerical_failure` или `nonconverged` и не
останавливает оставшиеся jobs.

Обычный персистентный путь остаётся без изменений.

## Терминальная сводка

CLI печатает имя experiment, режим и общее число jobs, затем по одному блоку
на каждую группу `(point, variant)` в порядке experiment-файла. Отдельные
job-блоки не печатаются.

Блок повторяет стиль CLI из commit `cfe424a` (`back to istok`) и содержит:

- число запусков и количества `success`, `nonconverged`,
  `numerical_failure`;
- для single-index — медианы начального и конечного `cosine_abs`;
- для multi-index — медианы начальной и конечной `projector_error`;
- эффективное `N_J`, медиану `outer_iterations` и количества причин
  остановки;
- профиль этапов с медианами времени и памяти по каждому этапу;
- медиану общего algorithm time, медиану tracemalloc peak и максимальный RSS.

Initial quality вычисляется из `result.beta_init` и ground truth после
успешного fit; persistent CSV-схема от этого не меняется. Для профиля сначала
вычисляются медианы времени и памяти каждого этапа, затем их доли пересчитываются
от сумм агрегированных значений, поэтому колонки долей согласованы между собой.

Агрегаты используют только конечные числовые значения. Пустая метрика,
неизвестная причина остановки или отсутствующий профиль отображаются как `—`.
Форматирование использует только стандартный Python и не добавляет зависимостей.

Код завершения остаётся `0`, если все jobs имеют статус `success`, и `1`, если
есть `nonconverged` или `numerical_failure`. `Ctrl-C` возвращает `130`.

## Проверка

Тесты подтверждают, что terminal-only режим:

- не создаёт output-каталог и не вызывает файловые/report функции;
- повторно использует одинаковые данные для paired variants;
- печатает один legacy-style блок на `(point, variant)` без per-job блоков;
- показывает mode-specific initial/final quality, статусы, `N_J`, итерации,
  stop reasons и агрегированный профиль;
- сохраняет status/error semantics и exit codes;
- отвергает комбинации с `--resume` и `--reports-only`;
- не меняет обычный персистентный workflow.

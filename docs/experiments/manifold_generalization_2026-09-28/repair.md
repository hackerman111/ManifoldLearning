# Исправление и повторная проверка manifold-generalisation

Дата: 2026-09-28. Исходные `main/`, `main_stop/`, их протокол и результаты
оставлены без изменений. Причины исходного провала установлены в
[`diagnosis.md`](diagnosis.md). Эта проверка сравнивает отдельный вариант
estimator с прежним режимом на одинаковых данных и случайных потоках.

## Спектральная обратная связь

Для смещения `v=x-center` и ортонормированных строк локального базиса `p_r`
исходная локализация использует числитель

`sum_r lambda_r * <p_r,v>² + alpha² * (||v||² - sum_r <p_r,v>²)`.

Значения `lambda_r` — относительные собственные числа *оценённой* локальной
структуры. Когда слабое, но истинное направление получает малое `lambda_r`,
ядро начинает включать далёкие точки вдоль него. Эти точки влияют на
следующее обновление; на плоском `m=3` это измеренная положительная обратная
связь. Новый явный `localization_spectrum="unit"` заменяет все `lambda_r`
только в **метрике локализации** на единицы. Базис, проверка ранга,
нормированный спектр результата и solver сохраняют исходную роль. Старый
`"relative"` остаётся умолчанием. Изменение класса `ESTIMATOR`.

Плотная формула для `unit`:

`||P v||² + alpha² * (||v||² - ||P v||²)`.

Она не требует массива различий `(J,n,d)` и вычисляется теми же блоками
центров. Входной массив собственных чисел не меняется.

## Что именно можно проверять по скалярному отклику

Для `m>=2` само поле `row(Dz(x))` не определяется одной функцией
`f(x)=||z(x)||²/2` без дополнительных ограничений на `z`. Например, при
`z(x)=(x1,x2)`, `R(x)` — поворот плоскости на угол `κ x3`, и
`z_tilde(x)=R(x)z(x)` функции `||z_tilde||²/2` и `||z||²/2` совпадают **во
всех точках**. Однако в точке `(1,0,0)` строки `Dz` порождают
`span(e1,e2)`, а строки `D z_tilde` — `span(e1,e2+κe3)` при `κ!=0`.
Обе карты гладкие и полного ранга в окрестности этой точки. Конструкция
вкладывается в `m=3`, оставляя третью координату без поворота, и применима
к исходной искривлённой карте. Поэтому восстановление выбранного
генератором `row(Dz)` на искривлённых `m>=2` не является проверкой
идентифицируемого параметра общего scalar-response manifold estimator.
Численные расстояния до этого поля всё равно полезны как описательная
диагностика; они не получают флаг `recovered`.

Для плоского `c=0` проверяется глобальное постоянное подпространство при
явной предпосылке об общей EDR-структуре. Для `m=1,c>0` одномерное
направление карты определяется градиентом `f` вне множества `z=0` с
точностью до знака; оно оставлено в проверке восстановления. Это не
гарантирует оценку при конечных `n` и шуме.

## Исправленные метрики и критерий

Новый запуск `experiments.manifold_generalization_repair` хранит четыре
пары `(RMS,max)` по синусам всех главных углов:

1. `center`: оценённый и точный базисы во **всех** 40 центрах;
2. `chart_estimation`: оценённый и точный базисы **того же** ближайшего
   центра для каждой из 512 query-точек;
3. `query_raw`: оценённый базис ближайшего центра против истинного базиса
   в query, как в старом опыте;
4. `query_oracle`: точный базис ближайшего центра против истинного базиса
   в query, то есть ошибка дискретизации даже при идеальной оценке.

Для идентифицируемых профилей `recovered` означает `center` и
`chart_estimation` RMS и max `<=0.2`. Порог не менялся. `query_raw` теперь
отчётная ошибка публичного nearest-chart правила, а не невозможный на
реализованных искривлённых выборках gate. Старое поле `recovered` и его
значения в `main_stop/` не пересчитываются. Исключения fit входят в
знаменатель; `recovered=false` для идентифицируемого профиля с ошибкой,
`recovered=null` для искривлённых `m>=2` независимо от ошибки.

Парный development-запуск: seeds 81000–81004, оба режима поддержки,
`m=1/2/3`, `c=0/.35/.8`, шум `0/.1`, оба спектральных режима, всего 360 fits.
Один BLAS thread, `n=600,d=8,J=P=40`, `scale_boundary="stop"`, остальные
параметры и потоки данных как в исходном exploratory `main_stop/`.
Первичная заранее записанная проверка варианта: все 10 плоских
`broad,m=3` fits должны пройти исправленный критерий без численных ошибок.
Остальные плоские профили нужны для обнаружения регрессий. Только после
прохода этой проверки допускаются untouched seeds 82000–82004 в плоских
профилях. После отрицательного development-гейта для искривлённых данных
их held-out проверка не запускается.

Воспроизведение:

```bash
UV_CACHE_DIR=/tmp/adp-uv-cache uv run --no-sync python -m experiments.manifold_generalization_repair --profile selection --out docs/experiments/manifold_generalization_2026-09-28/repair_selection --budget-seconds 600
UV_CACHE_DIR=/tmp/adp-uv-cache uv run --no-sync python -m experiments.manifold_generalization_repair --profile validation-flat --out docs/experiments/manifold_generalization_2026-09-28/repair_validation_flat --budget-seconds 600
```

Каждый каталог содержит `manifest.json` с версией, hashes исходников,
формулами и конфигурацией, `runs.jsonl` со всеми успехами/ошибками и
`summary.json`. `complete=false` означает частичный запуск. Время fit
измеряется `perf_counter`; RSS — накопительный high-water mark процесса,
его нельзя трактовать как независимый пик каждого fit.

## Результат

Обе серии завершены: development 360/360 и untouched flat validation
120/120. Сохранённые в `manifest.json` SHA256 всех 11 исходников совпадают с
текущими файлами. На плоской validation-серии широкий граф дал следующие
успехи по полному критерию (оба уровня шума, пять seed каждый):

| m | relative | unit |
|---:|---:|---:|
| 1 | 10/10 | 10/10 |
| 2 | 4/10 | 10/10 |
| 3 | 0/10 | 10/10 |

Численных ошибок в этих 60 fits нет. В development на тех же широких
плоских профилях `unit` также дал 30/30 против 15/30 у `relative` (одна
ошибка). Значит, заранее заданный flat m=3 gate подтверждён независимо;
`unit` с широким графом — проверенный вариант **только для этих плоских
профилей**. Median fit time на flat validation: 0.477 s (`unit`) и 0.560 s
(`relative`) по 30 fits; это сопутствующее наблюдение, не отдельный
производительный benchmark. Накопительный `ru_maxrss` достиг 100.5 MiB в
обеих группах и не является независимым пиком fit.

Узкий граф не прошёл стабильный gate: на flat validation `relative` получил
22/30 с шестью численными ошибками, `unit` — 19/30 с пятью. На искривлённых
development-профилях спектральная замена не устранила смещение центров;
их held-out validation по протоколу не запускалась. Эти данные не дают
оснований менять production default или объявлять восстановление
искривлённого manifold.

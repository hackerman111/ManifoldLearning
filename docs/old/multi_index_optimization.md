# Multi-index Average Derivative Procedure: оптимизация и граница качества

Дата: 2026-09-14. Исходная версия: `d6af01d8460595ed5c023f78d297cabb6c1cfd80`.
Измерения относятся к незакоммиченному патчу поверх этой версии.
Объект работы — `ADP.cli.main --mode multi`, а не `ADP_Manifold`.

## Сохранённая задача

В `multiindex.tex`, разделы multi-index Preliminaries и Alternating optimization,
используются локальные статистики `I_j`, `U_j`, коэффициенты `L_j` и общий
базис `B`. Реализация при фиксированных коэффициентах решает

\[
\min_B \sum_j mass_j\|I_j-U_jB^TL_j\|^2
       +\lambda\|B-B_0\|_F^2.
\]

Формы: `X=(n,d)`, `U=(J,P,d)`, `I=(J,P)`, `L=(J,m)`, `B=(m,d)`.
Новая версия статистик нормирует `I,U` локальной массой и передаёт эту массу
во внешний вес решателя. `mass` здесь не является Kish effective sample size
`(sum w)^2 / sum(w^2)`. Эти величины не подменялись.

Реализация HPAO включает свой trust/proximal механизм, QR/gauge compensation,
повторную локальную подгонку и критерии принятия шага. Это не буквальная
перепись каждого шага TeX: сохранено именно текущее поведение кода.
Внутренний множитель `1/2` в loss и все правила штрафа также сохранены.

Все изменения классифицированы как **EXACT**:

- Совместные действия оператора LSMR и CG выражены как
  `L @ B`, затем batched `U @ local`; сопряжённое действие —
  `U_j.T @ v_j`, затем `L.T @ pulled`. Межиндексные перекрёстные члены
  joint-задачи CG сохранены.
- Локальное `U @ B.T` вычисляется непосредственно через `matmul`.
- В локальной линейной инициализации исключены только строки нулевого веса.
  Передаётся явный `rcond=eps*max(n+d,d+1)`, соответствующий **исходной**
  расширенной матрице. Иначе `rcond=None` после screening мог бы изменить ранг.

Не изменены ядро, bandwidth, anisotropy, распределение направлений, seed,
центры, ridge, допуски, лимиты итераций, выбор внешнего шага и критерии отказа.
Смена суммирования допускает обычные различия floating point.

## Время и память

Intel Core i5-12400F, Linux x86_64, Python 3.13.12, NumPy 2.5.2, SciPy 1.18.1.
Один BLAS-поток: `OPENBLAS_NUM_THREADS=OMP_NUM_THREADS=MKL_NUM_THREADS=1`.
Версии обеих OpenBLAS-библиотек записаны в JSON каждого запуска.

Профилирование исходной задачи `(1000,100,100,20,2)` выявило повторяющийся
`einsum_path`: 7,09 из 11,80 секунды под `cProfile`. Это диагностическое
измерение, не число для расчёта ускорения.

Парные запуски полного обучения: `n=1000,d=100,J=100,P=20`, три seed,
3 внешних шага, до 3 принятых внутренних шагов, одинаковые данные и потоки
случайности для A/B; порядок A/B чередовался. Медианы секунд:

| m | Полное обучение до | После | Отношение медиан | Солвер до | После |
|---:|---:|---:|---:|---:|---:|
| 2 | 4,878 | 1,828 | 2,67 | 4,369 | 1,367 |
| 10 | 13,153 | 4,386 | 3,00 | 12,644 | 3,931 |

Максимальная Frobenius-разница проекторов A/B: `1,43e-9` для `m=2`,
`2,03e-8` для `m=10`. Максимальная разница качества: `4,14e-11` и `1,92e-9`.
RSS в этих отдельных процессах оставался около 89–91 MiB.
При `m=10` качество на этих данных остаётся низким (`q` около 0,73–0,77):
ускорение не является улучшением статистической оценки.

Полный runner включает `tracemalloc`; его накладные расходы входят в эти
времена, как и в штатный CLI. Некоторые замеры совпали по времени с запуском
проверок проекта; это не изолированный аппаратный стенд. Поэтому приводятся
медианы трёх seed и независимый микробенчмарк без tracing при измерении времени.

Микробенчмарк выполняет прогрев и 15 повторов; traced peak измеряется отдельно:

| J,P,d,m | Forward до, ms | После, ms | Относительная ошибка |
|---|---:|---:|---:|
| 100,20,100,2 | 0,146 | 0,035 | 3,74e-16 |
| 1000,20,1000,2 | 16,37 | 5,96 | 7,59e-16 |
| 1000,20,1000,10 | 22,56 | 6,23 | 7,68e-16 |

На больших массивах adjoint почти не ускорился: около 6–7 ms до и после.
Новый forward требует временный `(J,d)` вместо выбранного NumPy `(J,P,m)`:
для `J=d=1000` traced peak возрастает примерно с 0,48 до 8,16 MB при `m=2`.
Это явный обмен небольшой рабочей памяти на вычисления; общий `U` занимает
160 MB. Дополнительной постоянной копии `U` нет. Стоимость действия стала
`O(J*d*(P+m))` вместо выбранного ранее `O(J*P*d*m)`.

В инициализации локальная расширенная LS-матрица имеет `(k_j+d,d+1)` вместо
`(n+d,d+1)`. Доминирующая работа локальной факторизации зависит от `k_j*d^2`
вместо `n*d^2`; при почти полном support ускорение не обещается.
На `n=10000,d=100,J=500,P=20,m=2` после оптимизации солвера первый seed
занимал 29,54 s, из них 17,70 s — инициализация. После screening:
13,64 s всего, 3,17 s инициализации. Общий пик RSS практически не изменился:
369 против 370 MiB; теперь пик определяет поиск анизотропии.
На трёх крупных парных запусках максимальная разница проекторов после
6 внешних шагов — `1,22e-6`, разница нормированного качества — `9,68e-8`.
Это накопление округления в адаптивной процедуре; точность `1e-10` для
конечного базиса во всех режимах не заявляется.

`tracemalloc` не учитывает все native allocations. Поле `profile.total` хранит
максимальную прибавку traced-памяти по стадиям, а не полный RSS процесса;
для полного high-water используется отдельное поле `rss_peak_mib`.
Полное обучение при `n=10000,d=1000` не измерялось. Для такого режима одна
`X` требует 80 MB, `U` при `J=500,P=20` — ещё 80 MB; стоимость локальных SVD
в размерности 1000 остаётся самостоятельным ограничением.

## Что считать эффективным обучением

Универсального порога по одному `n/d` из этих опытов вывести нельзя.
Рабочий критерий качества для данной проверки:

\[
q=\frac{1}{m}\|P(I-P_*^TP_*)\|_F^2
 =\frac1m\sum_{a=1}^m\sin^2\theta_a\le0.1
\]

на каждом из трёх seed. Это среднее перекрытие подпространств не менее 90%,
а не ограничение максимального главного угла. CLI возвращает **ненормированное**
значение `m*q`. Число `0.1` — явно выбранный критерий эксперимента, не теорема.

Модель: `X~N(0,I)`, случайный ортонормальный истинный базис, `m=2`,
`Y=sum(sin(z_a)+0.25*z_a^2)+noise`, стандартное отклонение шума 0,05.
`N_loc=20`, `N_lin=max(40,floor(1.5*d))`, `J=max(100,ceil(n/20))`, `P=20`,
до 6 внешних шагов и 3 внутренних шагов, LSMR, локальная инициализация.
Остальные настройки — исходные defaults, полностью сохранённые в JSON.

| n | d=10: q, min–max | d=30: q, min–max | d=100: q, min–max |
|---:|---:|---:|---:|
| 500 | 0,0277–0,0427 | 0,0524–0,2237 | 0,4593–0,5173 |
| 1000 | 0,0046–0,0532 | 0,0354–0,0979 | 0,2000–0,4313 |
| 3000 | 0,0003–0,0282 | 0,0147–0,0390 | 0,2772–0,3368 |
| 10000 | 0,0003–0,0009 | 0,0194–0,0308 | 0,0729–0,1184 |
| 20000 | не измерено | не измерено | 0,0064–0,0732 |

Минимальные проверенные успешные точки: `n=500` при `d=10`, `n=1000`
при `d=30`. Для `d=100,n=10000` прошли только 2 seed из 3,
при `n=20000` — 3 из 3. Таким образом, на проверенной сетке переход для
`d=100` находится в интервале **(10000,20000]**, при `d=30` — **(500,1000]**;
для `d=10` известно лишь, что `n=500` уже достаточно по выбранному критерию.
Три seed не дают надёжной оценки вероятности успеха на новых данных.
Рост `n` не даёт монотонной гарантии при конечных центрах, направлениях,
локальной инициализации и фиксированном числе шагов.

На `n=20000,d=100,J=1000,P=20,m=2` конечный патч занимает 39,88–40,52 s,
RSS 1147–1158 MiB. При `n=10000` — 12,27–13,64 s и 363–386 MiB.
Это позволяет сопоставить критерий качества со своим бюджетом ресурсов;
абсолютный лимит времени или RAM пользователь не задавал.
В первой точке `n=20000` солвер занимает только 2,67 s из 39,88 s,
поиск анизотропии — 16,33 s, инициализация — 9,05 s. Даже бесплатный солвер
сократил бы это полное время лишь примерно на 6,7% при остальных равных.
Следующий предел масштабирования — массивы расстояний/весов `J*n` и их
повторный просмотр, а не число арифметических операций в joint-солвере.

Необходима также информативность sketch: при полном локальном ранге и `P<=m`
локальные коэффициенты могут интерполировать `I_j` без определения общего
подпространства. Текущий CLI уже требует `P>m`. По подсчёту размерностей
`J*(P-m)>=m*(d-m)` — необходимый общий ориентир для регулярной локальной
идентифицируемости, но не достаточное условие хорошего восстановления.

Внешний выбор `best` использует ошибку на центрах, которые по умолчанию входят
в training set. Это не независимая test-ошибка. На части точек ADP ухудшает
уже хорошую инициализацию; оптимизация вычислений это поведение сохраняет.
Успех по q не означает сходимость AO: в измерениях часто `converged=False`
из-за заданного бюджета шагов, при корректно принятых внутренних решениях.
Отдельная диагностическая точка CG `(1000,100,100,20,2)` не сошлась ни до,
ни после изменения: после 500 итераций остаток соответственно `2,425e-3`
и `8,677e-3`. Отказ сохранён в `cg_diagnostic.json`; его нельзя считать
успешным обучением или результатом с плохим q. Изменение порядка суммирования
не исправляет обусловленность normal equations. Числа обучения и границы
качества выше относятся к LSMR, а не к обещанию успешности CG во всех режимах.

## Воспроизведение и проверки

Артефакты: `benchmark_outputs/multi_optimization/` (JSON, базисы NPY).
`pairs/` — исходный код против окончательного патча; `operator.json` —
микробенчмарк; `grid/` и `grid_valid/` — качество после оптимизации солвера;
`grid_final/` — крупные точки после обоих изменений.
`grid_boundary_final/` повторно проверяет границы `d=10,30` на окончательном
патче. Предварительные отказы
валидации `J<ceil(n/N_loc)` в `grid/` сохранены, исправленные запуски лежат
отдельно в `grid_valid/`. Отказы не исключаются из файлов результатов.

Из корня репозитория, с установленным окружением проекта:

```bash
rtk proxy sh -c 'git show d6af01d8460595ed5c023f78d297cabb6c1cfd80:ADP/solver/LSMR.py > /tmp/multi_baseline_lsmr.py'
rtk proxy sh -c 'git show d6af01d8460595ed5c023f78d297cabb6c1cfd80:ADP/engine/initialize.py > /tmp/multi_baseline_initialize.py'
rtk proxy uv run --no-sync python -m benchmarks.multi_pairs --output /tmp/multi_pairs --reference /tmp/multi_baseline_lsmr.py --initialization-reference /tmp/multi_baseline_initialize.py
rtk proxy uv run --no-sync python -m benchmarks.multi_grid --output /tmp/multi_grid
rtk proxy uv run --no-sync python -m benchmarks.multi_grid --output /tmp/multi_large --n 10000 20000 --d 100
rtk proxy env OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 uv run --no-sync python -m benchmarks.multi_operator --output /tmp/multi_operator.json
```

В ограниченном окружении можно задать `UV_CACHE_DIR=/tmp/adp-uv-cache`.
Каждый запуск создаёт отдельный процесс; скрипты сетки и пар сами фиксируют
число BLAS-потоков. Seed данных и метода различаются; внутри runner потоки
для данных, шума, истинного базиса, центров, старта и направлений разделены
через `SeedSequence`. Направления изотропные и обновляются на каждом шаге.
Ядро: `K(t)=max(1-t^2,0)`, аргумент — квадрат анизотропного расстояния,
делённый на `h^2`. Bandwidth и анизотропия выбираются исходным поиском массы.

Проверено: 104 теста, включая плотный joint reference, adjoint identity,
неравные массы, strides, почти коллинеарные признаки, offset `1e9`, ridge
`0,1e-8,1e3`, сохранение rank cutoff; Ruff, Pyright, `uv lock --check`,
импорт `ADP`. Порогов по wall-clock в обычные pytest-тесты не добавлено.
